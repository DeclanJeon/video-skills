# 후반 총괄

## 입력
project JSON, 실제 pinned Handoff/snapshot/schema/편집 brief/profile/authority, receiver, source approvals와 필요한 별도 stem/graphic. [공통 실행 계약](../references/execution-contract.md)을 읽는다.

## 절차
1. 시스템·동일 프로그램을 먼저 점검하고 적합하면 재사용한다. 신규 설치가 필요하면 정확한 host/버전/의존성/위치/권한/network/비용/license/원복 계획을 실제 사용자에게 질문하고 명시 동의 후 설치한다. 작업 활성화는 설치 동의가 아니다.
2. `intake/validate`로 실제 source/approval/stream/range와 전체 요구 분모를 대조한다. 정본의 유일한 writer가 되어 production/foreign 데이터를 보존한다. 새 수령은 `IntakeRevision`으로 과거 snapshot/job을 남긴다.
3. 승인된 명시 work order를 `prepare`로 예약하고 해당 실제 Craft에서만 실행한다. 분야별 source/recipe/hash와 actual-consumed optional/derived lineage를 기록한다. 의미 변경·fake handle/stem·추가 agent·전송이 필요하면 별도 권한/입력을 요청한다.
4. 실행 후 `observe`의 native IDs/readback/full decode와 현재성을 대조한다. unknown/이미 성공한 작업은 재실행하지 않고 현재 process/files/journal을 조사한다. `progress`는 서로 다른 분모를 유지한다.
5. 고정 최종 파일의 보고된 전구간 시청·청취/coverage/조건 해소/권리를 QA로 받고 CAS 후 채택한다. 현재 receiver와 필수 master/variant/mix/stem/native/font 계약이 일치할 때만 로컬 납품한다.

## 반환
정본 revision/branch, 입력 수령 여부, work DAG·실제 reservation/job/artifact, scoped 영향/회복 조치, PG-E/PG0–PG6·필수 요구·분야·QA·납품 별 분모와 열린 사용자 질문. native 성공과 실제 인간/동의 진위 인증을 구별한다.
